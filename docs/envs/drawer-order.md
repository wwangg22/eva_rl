# `Rebot-DrawerOrder-v0` — articulated object + irreversible precedence

**Skill under test:** following an unknown kinematic constraint, and strict task ordering
with no gradient bridging the stages.

**Source:** `challenge/drawer_env_cfg.py`, `challenge/mdp/drawer.py`,
asset authored by `scripts/challenge/author_drawer_usd.py`
**Gym IDs:** `Rebot-DrawerOrder-v0` (1024), `-Play-v0` (16)
**Video:** `logs/videos/Rebot-DrawerOrder-Play-v0_settle.mp4`
**Test:** `scripts/test_drawer_env.py` — **passes**, four negative controls

## The task

Pull the drawer open by its handle, then put a block inside. The drawer always starts shut.

## Why this is a different skill

Two things the basket task never asks for:

1. **Articulated interaction.** The gripper must follow a kinematic constraint it does not
   know, applying force along the drawer's slide axis and nowhere else. A policy that
   "wants" to move off that manifold stalls or tears off the handle. The drawer joint has
   **zero drive stiffness** — it must be *dragged*, not driven to a setpoint — with light
   damping (8.0) so it stays where it is put instead of coasting.
2. **Irreversible precedence.** `block_to_drawer` is *hard-gated* on `drawer_is_open`, so
   the carry reward is exactly zero until the drawer is open. There is no smooth distance
   gradient bridging the two stages, unlike carrying an object toward an always-open
   basket.

`reach_handle` is gated the other way — it switches **off** once the drawer is open.
Ungated it becomes a comfortable local optimum: hovering at the handle of an already-open
drawer pays forever and the block never gets picked up.

## Asset

Generated by `scripts/challenge/author_drawer_usd.py` into
`source/reBot_RL/data/drawer/drawer.usda` (plain `pxr`, no Isaac Sim needed).

| part | detail |
|---|---|
| shell | 90 (x) × 130 (y) × 85 (z) mm, opening at −x (toward the robot), 6 mm walls |
| drawer | cavity 78 × 118 × 40 mm, mass 0.12 kg |
| handle | 20 mm bar, **22 mm standoff** from the drawer face |
| joint | `PrismaticJoint` along x, travel **−70 mm** (negative = pulled toward the robot) |
| plinth | 90 × 130 × **45 mm** static box the cabinet stands on |

The handle is a bar standing off the face so the fingers can straddle it **side-on** — this
arm has no top-down grasp below z = 0.19 m and could not reach over a lip (docs C1).

The cabinet stands on a **45 mm plinth at x = 0.265**, and both numbers are forced by
measurement rather than taste. The gripper cannot be positioned below **z = 44 mm** above the
table at all (docs C9), and the usable band is x ≈ 0.22–0.26 m. In the original design the
cabinet sat flat on the table at x = 0.29, putting the handle centre at **z = 26 mm** — below
the floor, so no policy could ever have touched it, and the task was quietly impossible. On
the plinth the handle sits at **z = 71 mm**. The drawer still travels *toward* the robot into
easier space as it opens.

> The smoke test asserts `handle_z > TCP_FLOOR` precisely so this class of mistake cannot
> recur silently.

> **Two authoring gotchas, both worth keeping.**
>
> The shell must be an ordinary rigid body anchored by a `FixedJoint`, **not** a kinematic
> body. PhysX articulations cannot contain kinematic links; making the shell kinematic causes
> the whole articulation to silently fail to parse with `"Pattern
> '/World/envs/env_*/Cabinet' did not match any articulations"`. Not obvious from the error.
>
> Geometry needs a bound **`UsdPreviewSurface` material**, not just `displayColor`. The RTX
> renderer ignores `displayColor`, so the first version of this asset rendered as a flat
> white box in which neither the drawer front nor the handle was distinguishable — which is
> exactly what made the earlier video illegible.

## MDP

**Actions — 7-D**, as all challenge envs. Note the drawer joint is **not** actuated by the
policy — it moves only through contact.

**Observations — 33-D**

| # | term | dim | slice |
|---|---|---|---|
| 1 | `joint_pos` | 8 | `0:8` |
| 2 | `joint_vel` | 8 | `8:16` |
| 3 | `block_pose` (root frame) | 7 | `16:23` |
| 4 | `drawer_state` — (opening fraction, is_open, block_in_drawer) | 3 | `23:26` |
| 5 | `actions` | 7 | `26:33` |

Term 4 makes the stage state observable, so the policy does not have to infer which phase
of the task it is in.

**Rewards**

| stage | term | weight | note |
|---|---|---|---|
| 1 | `reach_handle` | 2.0 | gated **off** once open |
| 1 | `opening` | **25.0** | dense credit for drawer travel |
| 2 | `reach_block` | 1.5 | |
| 2 | `lifting` | 8.0 | |
| 2 | `carrying` | 15.0 | **hard-gated on drawer open** — this gate *is* the precedence constraint |
| 2 | `success` | 60.0 | drawer open **and** block in the cavity |
| | `dropping_penalty` | −30.0 | |
| | `action_rate` / `joint_vel` | −2e-2 / −5e-3 | |

**Terminations:** `time_out` (16 s — two hard stages in sequence), `block_dropped`.

**Success:** drawer open past 70 % of travel **and** block inside the cavity (which now sits
at z = 50–100 mm, having moved up with the plinth). The cavity is
tracked in the *drawer's own frame* (its centre travels with the joint position), because a
fixed world-space box would either miss the cavity once the drawer is out or — worse —
accept a block sitting on the table in front of a shut drawer.

## Validation status

`scripts/test_drawer_env.py` — **passes**:

| check | result |
|---|---|
| articulation parses, single `DrawerJoint` | limits −70.0 .. 0.0 mm, as configured |
| handle clears the measured TCP floor | 71.0 mm vs 44 mm floor |
| drawer starts shut, `drawer_is_open` off | ✓ |
| opening fraction tracks the joint | 1.000 at full travel; off at half the threshold |
| `stowed` fires with the drawer open and the block in the cavity | 16/16 |
| **(a) precedence gate** — drawer *shut*, block placed exactly where the cavity would be | `stowed` off, carry reward **exactly 0** |
| (b) drawer open, block on the table | off |
| (c) drawer open, block hovering above the cavity | off |
| (d) drawer open, block below the cavity floor | off |
| carry reward gates **on** open | 0.0000 → 0.1747 |
| handle reward gates **off** open | 0.0319 → 0.0000 |
| nothing terminates on the first step after reset | ✓ |

Control (a) is the one that matters: it is the check that the task cannot be short-circuited
by shoving the block at a closed drawer.

**Still not verified:** that the arm can physically drag the drawer open. The joint is free
(zero drive stiffness, 8.0 damping) and the handle is now reachable, but no scripted pull has
been run end to end. That is the remaining gap for this env.
